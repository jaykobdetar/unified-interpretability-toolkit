# Observation contract

## Attention: one selected query head's last-query distribution

An optional closed `observation` object on a generation request is either absent or `{kind: "attention", head: integer}`. This mode requires `activation_site: "attention"`; the existing `layer` selects exactly one of 30 layers. Head is strictly 0–8, rejecting booleans. The pinned architecture has 9 query heads, 3 KV heads and width 64. Query head h uses KV head floor(h / 3). The module output already supplies attention weights in the installed Transformers 4.56.2 eager implementation; no backend switch or recomputation is needed.

The existing single observation hook reads only the selected head's **last consumed query**. A record adds `attention: {layer, query_head, kv_head, head_dim, query_position, key_positions, key_token_ids, probabilities, semantics}`. Each array has at most 160 entries, corresponding to actual consumed positions 0 through query_position; no padded or future keys are included. The actual maximum is 159 under 128 prompt tokens and 32 generation steps. Values are finite post-causal-mask softmax probabilities before value aggregation and projection. Eval dropout is zero. Each vector must sum to one within an explicit FP32 tolerance; it is not a weight matrix, activation magnitude, or attribution proof.

The UI shows a bounded probability table with meters, token positions and IDs, not a grid implying all-head/all-query coverage. Playback changes the selected step. It distinguishes prefill's last prompt query from decode queries. Attention for earlier prompt queries is not retained. No all-head/layer/step bank and no full prefill attention matrix are serialized. Comparison jobs display the edited branch observation, or the remaining baseline branch after edited EOS, with the existing branch label and prefix caveat. The baseline attention distribution is not promised by this contract. Without separate prompt-export consent, logs omit the entire key-token-ID array (including any generated-token keys); later history redaction removes it too. Probabilities/positions remain private observational data.

Qualification must independently reconstruct representative selected Q/K scores with the pinned architecture's rotary positions, KV repetition and causal mask, compare their softmax to captured values, verify normalization/key IDs/positions and unchanged output tokens/logits with observation on/off, and verify hook removal on controlled failures. Current eager execution and version are recorded; a future backend change needs new parity evidence.

## Logit lens: a selected residual read through final normalization and head

The alternative observation is `{kind: "logit_lens"}` and requires `activation_site: "block"`. The existing `layer` selects one block. For its last consumed residual after both residual additions, evaluate the actual model's final RMSNorm and tied output head under inference mode. This is a diagnostic projection of an intermediate residual, not an early-exit model, causal intervention, tuned lens, or calibrated probability estimate. No parameter is changed.

Each record adds `logit_lens: {layer, position, score_kind: "raw FP32 logits", lens_argmax_id, final_argmax_id, candidates, semantics}`. Candidates are the union of the lens top five and ordinary final top five, at most ten unique IDs. Each includes token text, `lens_logit`, `final_logit` and `delta_lens_minus_final`, with both values available. Full-vocabulary lens logits exist only transiently for the current step; they are not added to the retained comparison banks. The final and lens values use the same consumed prefix, but their difference is a readout comparison across processing depth, not an edit effect.

The UI displays the layer and residual semantics beside the score table, with a persistent diagnostic-readout caveat. It shares the existing step/replay controls. A request selects at most one observation mode, so attention and lens cannot silently combine their costs. Comparison jobs show the same explicitly labeled observation branch as their activation. The ordered edit list, if any, is still applied only between baseline and edited generations.

Qualification must compare the calculation against an independent uncached hidden-state reference, record all-vocabulary maximum error at layer 29 against the normal final output, verify representative earlier layers and exact on/off token/logit parity, and measure resource limits. Layer 29 should agree numerically within a declared rounding tolerance, rather than relying on a bit-exact assertion across different matrix-multiplication shapes.

## Prompt-pair captures: explicit positional alignment at one selected layer

The separate request mode is `{mode: "prompt_pair", prompts: [A, B], layer, activation_site, positions: [{a, b}, ...], preview_digest, source_model}`. Exactly two nonempty strings and the exact pinned source identity are required. Each prompt is limited to 2,048 UTF-8 bytes before tokenization and 1–128 encoded tokens; the complete request still fits the existing 8-KiB bound. No edits, generation limit or attention/lens observation is accepted in this mode. All layers 0–29 and the three defined capture sites are available, but exactly one layer/site is selected per job.

There are 1–8 unique position pairs. Each a/b is a strict nonnegative integer validated against its encoded prompt length. The UI must show tokenizer-produced IDs/positions for review before execution; tokenization uses the same pinned local tokenizer and has an explicit bounded preview path with no model load. The default suggested pair is each prompt's last token. No automatic semantic alignment, length truncation or name-based matching is allowed. Repeating a position on one side with a different counterpart is allowed and visibly explicit; duplicate pairs are rejected.

The model performs one uncached prefill for A, releases that output, then one for B, in the same fresh worker. A hook retains only selected positions at the selected layer/site. There is no generation or persistent KV cache. At most 8 × 3 × 576 scalars are serialized for vectors A, B and B−A: 24 vector-equivalents, within the current 32 × 576 activation-value budget. This uses at most eight trace records. Each pair records both native token positions and IDs, token-equality flag, consumed-prefix-equality flag, vectors and direct difference, L2 norms/distance and cosine similarity with a defined null value for zero norms. A difference between positions with equal token IDs may still reflect different preceding context.

The UI offers explicit pair editing, highlights token/position differences, and labels comparisons as positional, not semantic or causal. It provides pair stepping and the same ownership-safe cancel/reset behavior. Private logging uses the existing separate prompt consent; when off, prompt text and all source token IDs/pieces in these captures are redacted. Vector and summary exports remain private, bounded and explicit. Same-prompt/same-position pairs are a numerical identity check; different-prompt values are descriptive observations, not learned-pattern attribution.

Qualification includes strict schema/type/position tests, a same-prompt exact-identity case, independent vector subtraction/norm/cosine calculation, unequal-length explicit-position cases, actual source/hash preservation, cancellation/fresh-worker checks, and resource/output-size measurements. Prompt-pair preview and trace routing are a larger separate change whose runtime acceptance must follow the current capture/logging qualification.

## Shared implementation and acceptance boundaries

Metadata advertises implemented modes only. Unimplemented options stay absent from UI and runtime metadata. Step validators bound every extra field, reject nonfinite values and check mode/branch/source identity before accepting output. Existing scalar activation and paired-generation fields remain backward compatible. The UI never treats a selected viewer tensor or checkpoint-difference source as proof of an inference mapping; only the coordinator's pinned marker can authorize native edits.

Before shipping each mode, run focused helper/control tests followed by a serialized real-model reference and benign browser test, then update the feature ledger with exact source/runtime and limitations. Test-only patched controls handle error paths. Preserve failed attempts and earlier evidence. Physical-device and large-prompt performance remain unclaimed until exercised under the same limits.
