# Pinned owner acquisition

The owner CLI has a two-step data-only acquisition workflow. Browser model selection and HTTP routes cannot download, register, enable, or accept a license. The legacy `download` command remains disabled.

Supply a version-1 registry manifest with repository name, full 40-character commit, expected SHA-256 and exact size of every safe data file, and an accepted license plus its pinned license file. Branch labels, URLs, unknown packed formats, Python files, pickle, and unsafe auxiliary names are refused. Resolve and review the expected hashes independently before accepting the manifest; fetching a file and simply trusting its new hash is not expected-hash verification.

Run `atlas-model.py --config <owner-config> acquire-plan --manifest <manifest> --name <display-name> --max-bytes <explicit-budget>`. Review the complete returned manifest, payload bytes, reserve, and plan digest. Then the same owner can run `acquire` with the same arguments plus `--destination <new-directory> --plan-digest <reviewed-digest> --accept-license --timeout-ms <cooperative-duration-ms>`.

Only pinned HTTPS Hugging Face data URLs and a closed CDN redirect list are permitted. No authentication is loaded, no model is executed, and no automatic resume occurs. One acquisition per registry holds a disk reservation lock. Admission counts remaining payload, receipt metadata, explicit cache growth, and the existing 25 GiB reserve. Same-filesystem staging avoids a second payload copy. Each stream is size-bounded and hashed, then a Linux no-replace rename installs the directory. No existing owner directory is overwritten or evicted.

Successful acquisition re-verifies installed files through the existing registry and atomically publishes a disabled receipt, including reacquisition of an already enabled content identity. The returned enabled state is the state actually published. Owner `enable` is a separate choice. Standalone `register` retains its prior enabled-state behavior. Acquisition does not imply viewer compatibility, inference support, runtime fit, GPU support, or successful license/legal assessment. If the cooperative deadline expires after installation or bounded verification cannot finish before publication, the CLI returns exit status 2 with `installed: true, registered: false`; verified installed data remains at the chosen destination for owner registration. Incomplete transfers remove only their private staging directory.

Every recoverable installation-finalization failure reports retained data and `installation_durability`: parent-directory fsync confirmed or unconfirmed. A registry I/O error may occur after atomic receipt replacement; that outcome returns `registered: null, enabled: null, registry_publication: unconfirmed` with exit status 2. The owner must inspect the receipt before retrying or enabling; the CLI does not claim publication was absent and does not remove the committed installation. An existing receipt remains at its old source until replacement publication occurs.

The cooperative deadline is checked before/after every chunk and before installation/registration. The socket timeout is an idle-operation timeout of at most ten seconds, not a cumulative duration bound: buffered reads, connection/header processing or repeated successful receives can delay the next deadline check beyond that interval. There is no claimed maximum cooperative overshoot. Strict wall limits require an external hard supervisor with owned-process termination and confirmed cleanup. The reviewed plan includes this enforcement limitation. No live transfer or real-model acquisition was run for source qualification; retained tests use tiny in-memory streams and safe mocks. Shared runtime resource configuration is unchanged.
